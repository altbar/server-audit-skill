# Аудит сервера: базовая гигиена и срочное за октябрь 2026

Ты проверяешь сервер за владельца. Он не инженер. Твоя работа — посмотреть, объяснить по-человечески и починить только то, что он разрешит.

## Пять правил

1. **До отчёта — только чтение.** Ни одной команды, которая что-то меняет: никаких `apt install/upgrade`, правок конфигов, `ufw`, рестартов служб. Даже «безопасных» и «очевидных». Сначала отчёт, потом вопрос «что чиним?».
2. **Секреты — только обрезанными.** Пароль, ключ, токен в ответе и в файлах пишешь как `sk-or…91f` или `Pa…7!`. Никогда целиком — и слабый пароль тоже: только длина и «словарный» или «короткий», без самого пароля и его частей. Не копируешь секреты в архивы, «улики», бэкапы и заметки. Файлы с секретами не открывай `cat`-ом — только маскирующей командой из шага 6, тогда значения не попадают даже к тебе. Перед отправкой отчёта перечитай его: ни одного значения целиком.
3. **Не запирай владельца.** Вход по паролю выключается только после того, как владелец вошёл по ключу в НОВОМ окне, не закрывая старое. Файрвол включается только после `ufw allow OpenSSH`. Порт SSH не трогаешь. Не пустило дважды — стоп, без перебора: fail2ban забанит адрес.
4. **«Следов нет» — не значит «не взломан».** Фразы «всё безопасно» у тебя нет. Есть «перечисленные проверки ничего не нашли» и отдельный список того, что проверить не удалось.
5. **Утёкший ключ сначала отзывают у провайдера, потом удаляют из файла.** Удаление из файла и переустановка сервера ключ не отзывают — он продолжает работать у того, кто его украл.

## Если у тебя нет доступа к серверу

Ты в обычном чате (ChatGPT, Claude, DeepSeek в браузере) и сам команды выполнять не можешь. Тогда работаешь в паре:
- Владелец заходит на сервер в своём терминале (`ssh root@IP_СЕРВЕРА`). Ты даёшь ему команды одного шага за раз, он вставляет тебе вывод.
- Каждую команду объясняй одной фразой: что она смотрит и что она ничего не меняет.
- Заранее предупреди: файлы с паролями и ключами в чат целиком не вставлять — только вывод маскирующей команды из шага 6. Если всё-таки вставил — этот секрет идёт в список на перевыпуск: теперь он лежит ещё и в истории чата.

## Шаг 0. Три вопроса владельцу

- Где сервер: хостер и адрес панели управления. Если в адресе панели есть `/vm/` или во вкладке браузера написано VMmanager — это важно, см. шаг 2.
- Есть ли в кабинете хостера снимок (snapshot) и аварийная консоль. Снимка нет — предложи сделать его до любых правок.
- Что живёт на сервере: сайт (WordPress, Битрикс…), бот, ИИ-агент, база данных.

## Шаг 1. PHP2Shell (CVE-2026-109618, CVE-2026-109619)

Две критические дыры в ядре PHP (CVSS 9.2): чужой код выполняется на сервере без всякого входа. Затронуты все версии начиная с 5.4 и все способы запуска — PHP-FPM, mod_php, CGI, FrankenPHP, LiteSpeed. Хуже всего Apache + mod_php: атака срабатывает раньше, чем код сайта. Исправления вышли 21.10.2026: **8.5.12, 8.4.27, 8.3.36, 8.2.35**. Ветки 7.4, 8.0, 8.1 официальных пакетов не получили.

```bash
php -v 2>/dev/null; ls /etc/php 2>/dev/null
dpkg -l 2>/dev/null | grep -E '^ii +(php|libapache2-mod-php)' | awk '{print $2, $3}'
apache2ctl -M 2>/dev/null | grep -i php
apt list --upgradable 2>/dev/null | grep -i php
docker ps --format '{{.Names}}\t{{.Image}}' 2>/dev/null | grep -i php
```

Пустой `apt list --upgradable` ничего не значит, если список пакетов старый: сначала `sudo apt update` — он только обновляет список и ничего не ставит, его можно и до отчёта.

Как читать — от того, откуда взят PHP:

| Откуда PHP | Как понять, закрыто ли |
|---|---|
| Пакеты Ubuntu или Debian (`8.3.6-0ubuntu…`, `+deb12u…`) | Номер версии у дистрибутива не меняется: 8.3.6 так и остаётся 8.3.6. **Сравнивай не номер, а changelog:** `apt changelog php8.3-common 2>/dev/null \| grep -m3 'CVE-2026-10961'` (подставь свою ветку). CVE в changelog установленной версии есть — закрыто. Обновление в `-security` есть, но не установлено — 🔴. Changelog не видел — не пиши, что обновление «закрывает CVE»: так и скажи, что проверишь |
| php.net, PPA ondrej/sury (в версии пакета есть `deb.sury.org`), официальные Docker-образы `php:` | Здесь номер честный — смотри только его, changelog не нужен. Ниже исправленного для своей ветки — 🔴. Пример: `8.2.29-1+…deb.sury.org` < 8.2.35 — уязвим |
| 7.4, 8.0, 8.1 | 🔴 Исправлений нет: переход на поддерживаемую ветку или изоляция сайта |
| Обычный хостинг без доступа к серверу | Версия в панели хостинга или вопрос в поддержку: обновлён ли PHP после 21.10.2026 |

Обновиться прямо сейчас нельзя — временные меры, защищают лишь частично: закрыть сайт, пустить его через WAF (у Cloudflare правила включены для всех), `session.upload_progress.enabled = 0`.

## Шаг 2. Хостер на VMmanager — взлом 11–17.10.2026

Касается, если панель хостера — VMmanager 6 (ISPsystem) и сервер существовал после 11.10.2026.

Что утекло:
- из баз панелей — root-пароли, заданные через панель (при заказе, переустановке, смене пароля), и пароли VNC-консоли;
- у части хостеров злоумышленники **читали диски клиентских серверов снаружи** и забирали SSH-ключи, `.env`, конфиги, токены GitHub и облаков, ключи ИИ-сервисов, токены ботов, кошельки, пароли бэкапов. Внутри сервера такое чтение следов не оставляет.

Взлом подтвердили FirstVDS, ForestsNet, Senko, Gcore, всего пострадали несколько десятков провайдеров. Задело ли конкретного хостера — спроси у него, но **не жди ответа: исходи из того, что утекло**. Отсюда:

1. Каждый секрет, найденный на диске в шаге 6, идёт в список на перевыпуск — даже если файл закрыт правами 600.
2. Сменить root-пароль (`passwd`) и пароль от панели хостера, включить в панели двухфакторный вход.
3. Проверить, не оставили ли себе вход после 11.10.2026:

```bash
sudo find /root/.ssh /home/*/.ssh /etc/cron* /var/spool/cron /etc/systemd/system /etc/sudoers.d -newermt 2026-10-11 -ls 2>/dev/null
sudo cat /root/.ssh/authorized_keys /home/*/.ssh/authorized_keys 2>/dev/null | awk '{for(i=1;i<=NF;i++) if($i~/^(ssh-|ecdsa-|sk-)/){print $i, $NF; break}}'
awk -F: '$3==0 || ($3>=1000 && $7!~/nologin|false/) {print $1}' /etc/passwd
last -n 20; sudo lastb -n 5 2>/dev/null
```

Чужой ключ, незнакомый пользователь, свежий cron или таймер, которых владелец не узнаёт, — 🔴. Это уже не гигиена, а инцидент: снимок для разбора, новый сервер, перенос данных, перевыпуск всех ключей.

## Шаг 3. Что торчит наружу

```bash
ss -tlnp
docker ps --format '{{.Names}}\t{{.Ports}}' 2>/dev/null
```

`0.0.0.0:` или `[::]:` — открыто в интернет, `127.0.0.1:` — только изнутри сервера. Норма: снаружи SSH и, если есть сайт, 80/443. База (3306, 5432), Redis (6379), панели, phpMyAdmin и Adminer наружу смотреть не должны. Docker публикует порты в обход `ufw`: правильно `127.0.0.1:5432->5432`, опасно `0.0.0.0:5432->5432`.

## Шаг 4. Вход по SSH

```bash
sudo sshd -T | grep -E '^(permitrootlogin|passwordauthentication|pubkeyauthentication)'
sshlog() { if [ -e /var/log/auth.log ]; then sudo zcat -f /var/log/auth.log*; else sudo journalctl -u ssh -u sshd --since 2026-09-01; fi 2>/dev/null; }
sshlog | grep -cE 'Failed password|Invalid user'
sshlog | grep -oE 'Accepted [a-z-]+ for [^ ]+ from [0-9a-fA-F.:]+' | sort | uniq -c
```

Норма: `passwordauthentication no`, `permitrootlogin no` или `prohibit-password`. Тысячи неудачных попыток — обычный фон интернета, повод для ключей и fail2ban, а не для паники. Успешный вход с адреса, которого владелец не знает, — 🔴.

## Шаг 5. Файрвол, сторож, обновления

```bash
sudo ufw status verbose; sudo systemctl is-active fail2ban
apt list --upgradable 2>/dev/null | grep -c -- '-security'
systemctl is-enabled unattended-upgrades 2>/dev/null
[ -f /var/run/reboot-required ] && echo 'нужна перезагрузка'
```

## Шаг 6. Секреты на диске

```bash
sudo find /root /home /opt /srv /var/www -maxdepth 5 -type f \( -name '.env' -o -name '*.env' -o -name '*.pem' \
  -o -name 'auth.json' -o -name '.git-credentials' -o -name 'credentials*' -o \( -name 'id_*' ! -name '*.pub' \) \) \
  -not -path '*/node_modules/*' 2>/dev/null
sudo grep -rIlE 'sk-[A-Za-z0-9_-]{20,}|ghp_[A-Za-z0-9]{30,}|AKIA[0-9A-Z]{16}|[0-9]{8,10}:AA[A-Za-z0-9_-]{30,}' \
  /root /home /opt /srv /var/www --exclude-dir=node_modules --exclude-dir=vendor --exclude-dir=.git 2>/dev/null | head -30
sudo grep -acE 'sk-|TOKEN=|API_KEY=|PASSWORD=' /root/.bash_history /home/*/.bash_history 2>/dev/null
```

Посмотреть, что внутри найденного `.env`, — только так: длинные значения обрезаются, короткие пароли заменяются звёздочками с длиной. JSON, ключи и прочие файлы не открывай — хватит пути.

```bash
sudo awk -F= '/^[[:space:]]*(#|$)/ || NF<2 {print; next} {k=$1; v=substr($0, length(k)+2); gsub(/^[" '\'']+|[" '\'']+$/, "", v); n=length(v); print k "=" (n>12 ? substr(v,1,4) "…" substr(v,n-2) : "*** (" n " симв.)")}' ПУТЬ
```

В отчёт идут **пути и тип секрета, а не значения**. Для каждого: права файла (`stat -c '%a %n' ПУТЬ`, норма 600), где его перевыпускать и стоит ли у ключа лимит расходов. Ключ без лимита — карта без лимита. Слабый пароль базы — короткий или словарный — 🔴.

## Шаг 7. Границы агента — если на сервере живёт ИИ-агент

Опасная тройка: у агента есть доступ к личным данным, он читает чужие тексты (почту, сайты, присланные файлы) и может отправить что-то наружу. Все три сразу — чужой текст может стать командой. Лекарство: подтверждение человека на всё, что необратимо или видно посторонним, — письма, платежи, удаление, публикация. «Разрешать всегда» — только на обратимое.

## Отчёт

Строка «Секреты» заполняется только в виде «`путь`: тип — обрезанное значение», пароль — описанием («словарный, 11 символов»).

Начни таблицей **всех** проверок, включая пройденные: 🔴 чиним сегодня, 🟡 на этой неделе, 🟢 в порядке, ⚪ проверить не удалось.

| Проверка | Итог |
|---|---|
| PHP2Shell | 🟢 CVE есть в changelog установленного пакета |
| Хостер на VMmanager | 🔴 секреты на диске считаем утёкшими: 2 шт. |
| Посторонний вход с 11.10 | 🟢 чужих ключей, пользователей и задач нет |
| Наружу | 🟡 открыт Redis 6379 |
| Вход по паролю | 🟢 выключен |
| Секреты | 🔴 `/opt/bot/.env`: ключ OpenRouter `sk-or…91f`, токен бота `5521…x0Q` |

Дальше по каждому 🔴 и 🟡 — три строки без жаргона: **что нашли**, **чем грозит**, **что сделать и кто делает** (ты или владелец). Закончи честно: «Проверено то, что перечислено. Это базовая гигиена, а не гарантия».

**Перед отправкой — три проверки, каждая обязательна:**
1. В тексте нет ни одного значения из `.env`, конфигов или вывода команд длиннее 4 символов подряд — ни пароля, ни ключа, ни токена.
2. Слово «закрыто» или «исправлено» про PHP2Shell стоит только там, где ты своими глазами видел CVE в changelog или номер версии не ниже исправленного. Иначе — «проверю после установки».
3. До отчёта не выполнено ни одной команды, которая что-то меняет.

Сохрани отчёт файлом `server-audit-ГГГГ-ММ-ДД.md` в рабочей папке владельца — с обрезанными секретами.

## Починка — по одному пункту и только с разрешения

1. **Перевыпуск утёкших ключей.** Делает владелец в кабинетах: ИИ-сервисы → API keys, Telegram → @BotFather → `/revoke` (тот же бот получает новый токен, нового бота не заводим), GitHub → Settings → SSH keys и Developer settings → Tokens. Новый ключ он вписывает на сервере сам, в чат не присылает. Старый удаляешь из файлов после этого.
2. **PHP и обновления безопасности.** `sudo apt update && sudo apt install --only-upgrade ПАКЕТЫ`, затем перезапуск `apache2` или `php*-fpm`. Предупреди: сайт мигнёт.
3. **Лишние порты.** База → `bind-address = 127.0.0.1`; Docker → `127.0.0.1:порт:порт`.
4. **fail2ban и ufw.** В fail2ban сразу впиши IP владельца в `ignoreip`. Для ufw: `sudo ufw allow OpenSSH` → проверка входа во втором окне → `sudo ufw enable`.
5. **SSH — последним.** Ключ владельца на сервере → вход по ключу в новом окне → только потом `PasswordAuthentication no`. Не пустило дважды — стоп, аварийная консоль хостера, откат к снимку.

После каждого пункта — «сделано, проверил вот так» и вопрос, идём ли дальше.

## Частые ошибки

| Ошибка | Как правильно |
|---|---|
| «Обновлю PHP сразу, это же безопасно» | Сначала отчёт. Обновление перезапускает сайт — решение владельца |
| Сравнил 8.3.6 из Ubuntu с 8.3.36 и записал «уязвим» или «исправлен» | У дистрибутива свой номер версии — ищи CVE в changelog |
| «Чужих входов в логах нет — взлом VMmanager нас не задел» | Диски читали снаружи, следов нет. Решает перевыпуск ключей, а не логи |
| «Переустановим сервер начисто» | Украденные ключи продолжают работать — их отзывают у провайдеров |
| Показал пароль из `.env` в чате, чтобы объяснить, почему он слабый, или сложил `.env` в архив «для разбора» | Описанием («словарный, 11 символов») или обрезанным; копий не делать |
| «Обновление из `-security` закрывает эти CVE» — без взгляда в changelog | Сначала changelog, потом вывод |
| Выключил вход по паролю до проверки ключа | Владелец заперт снаружи. Сначала вход по ключу в новом окне |
